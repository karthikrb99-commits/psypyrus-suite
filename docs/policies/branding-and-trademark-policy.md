# Branding and Trademark Policy

## 1. Purpose

This policy defines how the PsyPyrus / Papyrus identity may be used in public, commercial, and derivative contexts.

It exists because the codebase is Apache 2.0, but brand identity is not the same thing as code rights.

## 2. Protected Identity Elements

The following are part of the project identity and may be protected or restricted separately from the source code licence:

- project names: **PsyPyrus**, **Papyrus**, and related product names
- logos, symbols, marks, badges, and icons
- visual identity systems
- slogans and campaign language
- official-looking marketing assets
- website, package, or app-store presentation that suggests affiliation

## 3. Basic Rule

Do not use project branding in a way that is confusing, misleading, or falsely implies official endorsement, sponsorship, or institutional alignment.

That includes claims of:

- official government sponsorship
- official national mission status
- exclusive authorization
- partnership or certification that does not exist
- being the original source when the build is a derivative

## 4. Allowed Mentions

You may generally use the project name descriptively to:

- refer to the upstream repository
- describe compatibility or lineage
- acknowledge use of the codebase in documentation
- state that a deployment is based on the project, provided the statement is accurate and not deceptive

## 5. Restricted Uses

The following require explicit permission if they are to be used publicly:

- product logos and marks in a shipping app or service
- official-looking brand kits
- domain names or subdomains that could be mistaken for the canonical project
- app store names or social profiles that impersonate the upstream project
- commercial packaging that removes upstream attribution while retaining project identity value

## 6. White-Label and Rebrand Guidance

If someone wants to white-label or rebrand the product, the following baseline rules apply:

- do not imply the white-labeled build is the upstream project
- do not remove required source attribution or licence text
- do not use protected names or marks without permission
- do not present the derivative as the official public mission platform unless that is true and documented
- keep the derivative clearly distinguishable from the upstream identity

## 7. Mission Framing

The project may be described as mission-aligned with a public mental-health infrastructure objective.

That does **not** mean the project is:

- a government department
- a statutory authority
- an officially sanctioned national programme
- a public health instrument unless formally adopted by such an entity

Use mission-aligned language carefully and truthfully.

## 8. Attribution Standards

Where appropriate, downstream materials should preserve or reproduce:

- upstream project name
- notice of derivation
- licence reference
- source repository reference
- author or contributor acknowledgements

## 9. Support and Endorsement

No use of the project identity may suggest support, certification, audit approval, or clinical endorsement unless a written statement says so.

## 10. Enforcement

The project owners may request correction, removal, attribution restoration, or takedown of misleading use of brand identity.

Repeated misuse may result in denial of permission for branding or commercial collaboration.
