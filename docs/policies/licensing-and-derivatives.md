# Licensing and Derivatives Policy

## 1. Governing Licence

The source code in this repository is currently licensed under **Apache License 2.0**. That licence governs the code unless a file, directory, or future commercial agreement explicitly says otherwise.

Apache 2.0 is permissive. It allows modification, redistribution, and derivative works, including forks and ports, provided the licence conditions are met.

## 2. What Apache 2.0 Means Here

Apache 2.0 generally permits downstream use of the code, including commercial use, but it also requires respect for:

- copyright notices
- licence text
- NOTICE file requirements, where applicable
- patent terms and patent retaliation provisions
- attribution and provenance requirements in distributed source form

Apache 2.0 does **not** automatically give permission to use trademarks, brand assets, or names in a confusing or misleading way.

## 3. Derivative Works Are Allowed, But Not Misrepresentation

A fork, clone, port, or derivative build may be legally possible under Apache 2.0, but the derivative must not:

- misrepresent itself as the original project
- imply official backing, endorsement, or affiliation without permission
- strip required notices or attribution
- remove or obscure provenance in source distributions where notices are required
- claim ownership over upstream work

## 4. Source Code vs Brand and Identity

This project separates:

- **code rights**: governed primarily by Apache 2.0
- **brand rights**: governed by trademark and branding policy
- **commercial deployment rights**: governed by separate commercial terms, if any

If a downstream builder wants to ship a white-label or rebranded product, that may still require separate brand permission even when the code itself is Apache-licensed.

## 5. White-Label, Rebrand, and Commercial Permission

Apache 2.0 alone does not create a white-label right to use the project name, logo, visual identity, or official mission framing.

Any of the following may require separate permission:

- white-label distribution
- rebranding for a commercial service
- use of the PsyPyrus or Papyrus names in a market-facing product
- use of logos, badges, mascots, slogans, or identity system assets
- public claims of official alignment with a national mission or public program

## 6. Provenance Standard

Where the licence or a later agreement requires attribution, downstream users should preserve:

- original copyright notices
- Apache 2.0 licence text
- NOTICE content, if present
- visible authorship or source references in documentation or about screens
- any prescribed “built with” or “powered by” notice

## 7. Mission-Aligned Derivatives

Derivative deployments intended for hospitals, NGOs, universities, or public-benefit programs are encouraged to retain the project’s mission-aligned safety and access values:

- clinician-first workflows
- patient safety controls
- supervision and referral support
- auditability
- interoperability
- low-resource deployment options

## 8. When Apache 2.0 Is Not Enough

If the goal is to **forbid** commercial reuse, white-labeling, or rebranding at the code level, Apache 2.0 is not the right only licence, because it is designed to be permissive.

In that case, the repository would need a different legal strategy, such as:

- a separate commercial licence for downstream deployers
- a source-available licence with tighter redistribution terms
- a dual-licence structure

## 9. Enforcement

Violations of licence terms, brand misuse, or false affiliation claims may lead to:

- takedown requests
- permission revocation for brand assets or commercial use
- legal action where applicable
- refusal of support or partnership

## 10. Practical Rule

**Code may be Apache 2.0; brand and commercial identity may still be protected.**

That is the cleanest posture for a project that wants open collaboration without giving up control over identity, trust, and public-facing representation.
